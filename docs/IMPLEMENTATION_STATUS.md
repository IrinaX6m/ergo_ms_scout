# Статус реализации SCOUT

Дата обновления клиента: 6 ноября 2026 года. Серверные результаты ниже относятся к 13 октября 2026 года.

Текущие задачи ведутся в [BACKLOG.md](../BACKLOG.md), принятые решения — в [DECISIONS.md](DECISIONS.md).

## Граница текущего этапа

Актуальные цели находятся в [DECISIONS.md](DECISIONS.md). Реализованы ручные селекторы и HTML-обход до 200 страниц. По прямому поручению пользователя реализован клиент ручного сбора с отдельным подтверждением плана. Визуальный выбор, настройка с LLM, управление профилями прокси и подключение машин ещё требуют реализации. Нагрузочная проверка 10 000 страниц не проводилась. Демонстрационный Docker-стенд удалён.

## Новый клиент ручного сбора

6 ноября 2026 года [Scout PR №1](https://github.com/ergoms/ergo_ms_scout/pull/1) влит в `dev` коммитом [`cad2547`](https://github.com/ergoms/ergo_ms_scout/commit/cad254748108756b2a43f6bd299f77384d746039).

- Шесть этапов: режим → источник и правила → предпросмотр → подтверждение → сбор → результат. Подтверждение доступно только для загруженного задания, совпадающего хеша плана и неизменённого черновика с непустым предпросмотром.
- На первом экране представлены три режима. Выбор кликами и предложение ИИ явно недоступны до появления соответствующего контракта SYSTEM. Эти экраны не вызывают выдуманные операции; переход к ручным правилам сохраняет адрес источника.
- Порядок обработки показан как загрузка → обход ссылок → извлечение → записи. Числа берутся из ответа сервера; процент выполнения не выдумывается. Пауза и отмена ожидают состояния сервера.
- Настройки системы открываются через существующий интерфейс ядра; правила и ограничения сбора находятся в задании. Светлая, тёмная и автоматическая темы используют механизм и цветовые переменные ERGOMS.
- Форма, подтверждение и результаты адаптированы к узким экранам. Результаты используют DataTable ядра, клиентскую пагинацию всего полученного массива и просмотр происхождения поля; значения 0 и false сохраняются.
- Визуальный выбор, настройка с ИИ и выдача результатов порциями на сервере остаются задачами API-002, AI-001 и API-003.

Проверки клиента запускаются из корня ERGOMS: `ergoms npm --prefix=../../modules/scout/client run test:workflow` и `ergoms npm --prefix=../../modules/scout/client run test:browser`. Браузерная проверка собирает настоящие компоненты с явно тестовым API в локальную HTML-страницу в `virtual_env/cache/tmp/scout-client-browser`; она не проверяет живой Django/Celery. Общие проверки: `ergoms npm run lint:check` и `ergoms npm run build`.

Перед слиянием на коммите [`c7828bd`](https://github.com/ergoms/ergo_ms_scout/commit/c7828bd1f8f62f8d1fdd7ee1fe75d022c1cec464) прошли 7 модульных тестов, ESLint для Scout и браузерный сценарий на закреплённой версии клиентского ядра ERGOMS. Браузерная проверка охватила подтверждение полного серверного плана с несколькими адресами и правилами, снятие блокировки при мгновенной паузе во время загрузки записей, возврат к предпросмотру, потерю связи, происхождение значений, пагинацию 25 записей, темы и ширины 320–1440 px.

После слияния на коммите `e7cb2f5` основной ручной сценарий прошёл через `/scout` на живых Django, Celery и Media API. На локальной HTML-странице предпросмотр и сбор дали по три записи. JSON и CSV скачались из интерфейса и содержали ожидаемые строки. Отдельный запрос к API подтвердил, что запуск без подтверждения плана возвращает HTTP 409.

По сообщению заказчика проверка UX-003 для ручного сценария прошла без замечаний.

## Сделано

Фазы 0 и 1: модуль `scout` в `modules/scout`.

- Приложение Django, права `scout_view`, `scout_configure`, `scout_run`, `scout_review`, `scout_export`, страница `/scout`, пункт меню.
- Задание, версия плана, запуск, задача, попытка, снимок страницы, версия схемы, версия правил, запись, доказательство поля, файл выгрузки.
- Предварительная загрузка HTML в `virtual_env/cache/scout/snapshots/`.
- Правила CSS и XPath по сохранённому снимку. CSS в этой версии: тег, класс, идентификатор, вложение и прямой потомок. Селекторы с атрибутами, запятой и псевдоклассами отклоняются.
- Сервер отклоняет основной сбор, если план этой версии не подтверждён.
- Одновременно допускается один незавершённый сбор.
- Извлечение идёт задачей Celery. Повтор с тем же снимком и теми же правилами не создаёт вторую запись.
- Просроченная аренда задачи возвращает её в очередь и не удаляет запуск.
- Поздний ответ старой попытки не записывает результат.
- JSON и CSV пишутся через media_api, клиент получает подписанную ссылку.
- Команды `ergoms scout:collect` и `ergoms scout:approve-run`.
- После сохранения задания форма снова читает название, адрес и поля по `?job=`.
- У запуска есть журнал. Если снимок уже лежит на диске, строки журнала считаются по этому файлу, а не по старым сообщениям.
- Ответ `gzip` и `deflate` распаковывается до записи снимка. Уже сохранённый файл с сигнатурой gzip при чтении тоже становится HTML. Селектор смотрит распакованную страницу.
- «Подтвердить план» и «Начать сбор» активны только пока запуск в статусе `awaiting_confirmation`. На завершённом запуске эти кнопки ничего не делают. Новую загрузку начинает «Загрузить страницу».
- Запись строится по селектору карточки. Поле карточки читается внутри неё, пустое значение не сдвигает следующую карточку. Без селектора карточки на странице одна запись. «Сохранить изменения» правит текущее задание, «Новое задание» начинает другое.
- Паузу можно продолжить. Просроченная аренда во время паузы или отмены доводит запуск до `paused` или `cancelled` и не оставляет его в переходном состоянии.
- Повтор задачи будит очередь сам и раз в 30 секунд через расписание Beat. Ключ загрузки — хеш адреса, не сам адрес. Локатор доказательства не ограничен 500 символами.
- XPath `string()` и `count()` дают одно значение, а не разбор строки по символам. Кодировка берётся из BOM, charset ответа, meta и запасного варианта utf-8, затем cp1251.
- «Получить предпросмотр» сохраняет план и готовит пример результата. Подтверждение и старт находятся на отдельном этапе; сервер проверяет хеш плана. По умолчанию собираются только указанные страницы. Режим «Обойти сайт» после подтверждения идёт по ссылкам в пределах сайта, глубины и потолка страниц. Загрузка, обход ссылок и извлечение — разные задачи. Журнал лежит в «Подробностях выполнения».

13 октября 2026: редирект сохраняет глубину найденной страницы, более короткий путь возвращает адрес, пропущенный из-за глубины, кириллический домен и punycode задают одну границу обхода. Изолированные тесты этих случаев прошли. Живой worker после перезапуска повторил прежние 14 сценариев и новые случаи redirect, цепочки и короткого пути. Полный `ergoms api test modules.scout.api --full --noinput` снова остановился до тестов на миграции CRM. Приёмка 2A открыта: не проверены потеря процесса worker, гонка двух процессов и запоздалый ответ при смене маршрута. Факты — в `docs/PHASE_2A_REPORT.md`.

Воркер подхватывает код карточек и распаковки только после перезапуска `ergoms start-worker --module=scout` или задачи `start-worker --worker=all`. `ergoms stop` останавливает службы. Закрытие Cursor — нет.

## Не сделано

- Поиск по теме «Станки» и поисковые провайдеры.
- Клик по элементу сохранённой страницы и предложение полей карточек.
- Редактор блоков.
- Языковая модель.
- Исполнитель на другом языке. Конверт операции описан в `api/contracts/envelope.py`, вызывает его пока только Python в том же процессе.
- Очереди ролей `scout_search`, `scout_fetch`, `scout_browser`, `scout_crawl`, `scout_extract`, `scout_quality`, `scout_export` не созданы. Сейчас одна очередь `scout`.
