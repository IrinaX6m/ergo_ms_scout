## Сделано

Фазы 0 и 1: модуль `scout` в `modules/scout`.

- Приложение Django, права `scout_view`, `scout_configure`, `scout_run`, `scout_review`, `scout_export`, страница `/scout`, пункт меню.
- Задание, версия плана, запуск, задача, попытка, снимок страницы, версия схемы, версия правил, запись, доказательство поля, файл выгрузки.
- Предварительная загрузка HTML в `virtual_env/cache/scout/snapshots/`.
- Правила CSS и XPath по сохранённому снимку. CSS в этой версии: тег, класс, идентификатор, вложение и прямой потомок. Селекторы с атрибутами, запятой и псевдоклассами отклоняются.
- Сервер отклоняет основной сбор, если план этой версии не подтверждён.
- Одновременно допускается один незавершённый сбор.
- Извлечение идёт задачей Celery. Повтор с тем же снимком и теми же правилами не создаёт вторую запись.
- Просроченная аренда задачи возвращает её в очередь и не удаляет запуск.
- Поздний ответ старой попытки не записывает результат.
- JSON и CSV пишутся через media_api, клиент получает подписанную ссылку.
- Команды `ergoms scout:collect` и `ergoms scout:approve-run`.
- После сохранения задания форма снова читает название, адрес и поля по `?job=`.
- У запуска есть журнал. Если снимок уже лежит на диске, строки журнала считаются по этому файлу, а не по старым сообщениям.
- Ответ `gzip` и `deflate` распаковывается до записи снимка. Уже сохранённый файл с сигнатурой gzip при чтении тоже становится HTML. Селектор смотрит распакованную страницу.
- «Подтвердить план» и «Начать сбор» активны только пока запуск в статусе `awaiting_confirmation`. На завершённом запуске эти кнопки ничего не делают. Новую загрузку начинает «Загрузить страницу».
- Запись строится по селектору карточки. Поле карточки читается внутри неё, пустое значение не сдвигает следующую карточку. Без селектора карточки на странице одна запись. «Сохранить изменения» правит текущее задание, «Новое задание» начинает другое.
- Паузу можно продолжить. Просроченная аренда во время паузы или отмены доводит запуск до `paused` или `cancelled` и не оставляет его в переходном состоянии.
- Повтор задачи будит очередь сам и раз в 30 секунд через расписание Beat. Ключ загрузки — хеш адреса, не сам адрес. Локатор доказательства не ограничен 500 символами.
- XPath `string()` и `count()` дают одно значение, а не разбор строки по символам. Кодировка берётся из BOM, charset ответа, meta и запасного варианта utf-8, затем cp1251.
- «Получить предпросмотр» сохраняет план и готовит пример результата. Подтверждение и старт находятся на отдельном этапе; сервер проверяет хеш плана. По умолчанию собираются только указанные страницы. Режим «Обойти сайт» после подтверждения идёт по ссылкам в пределах сайта, глубины и потолка страниц. Загрузка, обход ссылок и извлечение — разные задачи. Журнал лежит в «Подробностях выполнения».

13 октября 2026 проверены глубина после редиректа, повторная постановка при обнаружении более короткого пути и совпадение границ обхода для кириллического домена и punycode. После перезапуска воркер повторил прежние 14 сценариев и новые случаи редиректа, цепочки и короткого пути. Полный `ergoms api test modules.scout.api --full --noinput` тогда остановился на миграции CRM. Подробности того прогона в [PHASE_2A_REPORT.md](PHASE_2A_REPORT.md).

Воркер подхватывает код карточек и распаковки только после перезапуска `ergoms start-worker --module=scout` или задачи `start-worker --worker=all`. `ergoms stop` останавливает службы. Закрытие Cursor — нет.

## REL-001 — восстановление сбора на живом воркере

6 ноября 2026 на `c1da0de` проверен обход сайта через HTTP API Django, отдельные процессы Celery и Beat и временную базу PostgreSQL. Для брокера использовалась отдельная SQLite. Контрольный каталог состоит из стартовой страницы и страницы по ссылке. Контрольный сбор дал две сохранённые страницы и три записи. Для имитации сбоя HTTP-сервер задерживал ответ второй страницы, пока воркер не был принудительно остановлен. Использовались штатные 120 секунд аренды и проверка Beat каждые 30 секунд.

- После остановки первая попытка получила `lease_lost`. Новый воркер повторил загрузку, сбор завершился в `completed` с теми же двумя снимками и тремя записями.
- Во время повторной загрузки второй живой воркер получил дубликат сообщения и вернул `changed: false`. Повтор старого сообщения после завершения также оставил записи и снимки без дублей.
- При сбое в `pausing` просроченная попытка получила `lease_lost`, а запуск перешёл в `paused`. Загрузка возобновилась по команде «Продолжить» и завершилась с теми же двумя снимками и тремя записями.
- При сбое в `cancelling` запуск перешёл в `cancelled`, потерянная загрузка больше не выдавалась. В отдельном прогоне воркер получил запоздалый HTTP-ответ уже после команды отмены. В обоих случаях сохранились только снимок и запись, созданные до отмены.

На свежем ядре ERGOMS эти сценарии повторены со штатным запуском отдельных воркеров Scout и `SCOUT_WORKER_DB_REUSE_MAX=50`. Beat восстановил потерянную задачу после 120 секунд аренды. После возобновления паузы сбор вернул те же три записи и два снимка. При отмене после падения и при позднем ответе живого воркера сохранились одна ранее записанная строка и один снимок. Воркеры проигнорировали повторную доставку во время новой попытки и сообщение от первой попытки после завершения. Замеры подключения к PostgreSQL приведены в [SPEC-003](SPEC_003.md#проверка-штатного-запуска-воркеров).

После объединения запросов диспетчера REL-001 повторён на живых Celery, Beat и PostgreSQL. Сбор восстановился без дублей, продолжился после паузы и сохранил только уже записанные данные при отмене и позднем ответе. В журнале Beat подтверждён 30-секундный интервал. Замеры приведены в [SPEC-003](SPEC_003.md#объединение-запросов-диспетчера).

При обновлении проекта примените миграцию `scout.0008_run_dispatch_requested_until` командой `ergoms db-migrate` перед запуском обновлённых Django и воркеров Celery.

## SITEMAP-001 — обход по XML-карте

Сервер и CLI принимают адрес отдельной XML-карты `urlset`. Задача карты запускается после подтверждения плана и регистрирует страницы на глубине 0 в общей очереди обхода. Для них действуют обычные ограничения, в том числе рабочий предел в 200 страниц. Формат и состояния ошибок описаны в [контракте](API_CONTRACT.md#sitemap-001--xml-карта-сайта). Изменения не требуют миграции.

Проверки API и тестового HTTP-сайта покрывают запрет старта до подтверждения, загрузку gzip-карты, дедупликацию, фильтр пути и хоста, недоверенный порт, лимит страниц, 404, редирект за пределы плана, некорректный и пустой XML, DTD и неподдерживаемый индекс карт.

На изолированном стенде с Django, Celery и PostgreSQL проверены два запуска через HTTP API. Корректная карта загружена один раз после подтверждения; две страницы дали две записи с Evidence, лишние адреса не запрашивались, причина остановки — `max_pages`. Битая карта завершила запуск с `sitemap_invalid` и без записей. Полный набор из 86 серверных тестов Scout прошёл.

## SPEC-002 — разные правила для каталога и страниц товаров

Сервер поддерживает `crawl.page_types`, проверяет покрытие типов в предпросмотре и сохраняет использованные селекторы в версии правил и Evidence. Схема результата общая. Планы без типов продолжают работать с `extract_on`. Миграция не требуется. [Контракт SPEC-002](API_CONTRACT.md#spec-002--правила-для-типов-страниц)

На изолированном стенде с Django, Celery, PostgreSQL и Media API каталог дал две записи и шесть Evidence. Каталог использован только для ссылок, повторный адрес из карты и HTML загружен один раз. JSON и CSV сверены с API, нулевой остаток сохранился. Конфликт после редиректа на контрольном адресе заблокировал подтверждение с HTTP 409. Конфликт на странице, обнаруженной в основном сборе, дал `completed_with_errors` и сохранил запись с другой страницы. План старого формата дал две записи. Все 93 серверных теста Scout прошли.

## SPEC-001 — идентичность товара по SKU

Профиль `identity` в плане объединяет наблюдения одного SKU в каждом запуске, сохраняет Evidence всех источников и использует устойчивый ключ товара между запусками одного задания. Данные плана и результата добавляет миграция `0012_product_identity`. [Контракт SPEC-001](API_CONTRACT.md#spec-001--идентичность-товара)

На стенде с Django, PostgreSQL, двумя воркерами Celery и Media API выполнены два сбора. Каждый дал три строки и шесть Evidence у SKU `K-01`. Ключ товара совпал, цена изменилась с 1250.00 на 1350.00, первый результат сохранился. Проверены подписанные JSON и CSV. Четыре повторные доставки через брокер не изменили записи и Evidence. Отдельный сбор с разными ценами на двух URL сохранил оба значения и пометил конфликт цены. План прежнего формата вернул четыре отдельные строки. Все 98 серверных тестов Scout прошли.

## EXT-002 — сравнение запусков по SKU

API сравнивает выбранное поле в двух завершённых запусках одного задания с одинаковым хешем плана и профилем SKU. Ответ содержит полноту обеих сторон, общие счётчики, строки без ключа и порции изменений с Evidence. Изменений схемы БД нет. [Контракт EXT-002](API_CONTRACT.md#ext-002--api-сравнения-запусков)

На живых Django, PostgreSQL и двух воркерах Celery исходный сбор дал три строки, полный повторный — четыре. Изменение цены `K-01` с 1250.00 до 1350.00 подтверждено двумя Evidence на каждой стороне, а `K-03` получил `added`. В каждом запуске отдельно посчитана одна строка без SKU. При HTTP 404 у `K-02` частичный повторный сбор вернул `not_checked` и сохранил известные изменения. Проверены также `not_seen_before` после частичного исходного сбора, `not_seen` после полного обхода без ссылки на товар и постраничная выдача. Все 101 серверный тест Scout прошли.
