## Кто делает первым и что дальше

Начать с **UX-004** на действующем экране: прототип связанного выбора «снимок ↔ дерево ↔ инспектор», исправление слишком широкого выбора, клавиатура и узкий экран. Результат направляемой проверки записан в UX.md: требуется улучшить переключение областей и обнаружение кнопок. Клавиатура и ошибки остаются технически проверенными сценариями, не пользовательской приёмкой. SYSTEM реализовал и проверил [API-004 v1](../API_CONTRACT.md#api-004--dom-дерево-снимка): ветви, узел/предки, окно соседей и поиск. Использовать работающий API при проверке сценария; замечания по данным передать SYSTEM, не ждать финального визуального оформления.

Текущий клиентский цикл реализовал **DES-006** в темах ERGOMS; FE-005 включён на `/scout`. Прежний порядок сохраняется для новых изменений: DES-006 оформляет согласованное взаимодействие. После согласования данных — **FE-005**, развивая существующие компоненты. Порядок подключения: API-002 `ready`/HTML и `tree_version` → корни → ветви при раскрытии → узел/предки при клике в снимке → поиск по всем узлам → проверка правила API-002 с версией. Маршруты работают и проверены на живом Django/Celery. Условные примеры годятся для макетов, интеграция проверяется с реальными UUID/версиями/курсорами. Поиск охватывает и не раскрытые в клиенте ветви; дерево загружается частями. **FE-004** проверяет новый полный сценарий с настоящим API. UX-003 для ручного режима и базовый UX-001 заново не переоткрывать.

Прочие подключения идут по FE-001–FE-003: сервер ИИ, профили прокси и серверная пагинация уже готовы. Приоритет между этими подключениями и новым инспектором определять явно; наличие нового дизайна не означает завершения остальных клиентских задач.

Для FE-002 использовать ошибки `cloudflare_challenge`, `yandex_captcha` и `captcha_required`. Показывать `error.detail` или `error_summary` и отмечать частичный результат. [Контракт](../API_CONTRACT.md#anti-001anti-002--обнаружение-страниц-проверки).

## Границы

Код — `client/**`, включая переводы; документы — UX.md, DESIGN.md и согласованные макеты. Применять тему и компоненты ERGOMS. Изменение общего ядра оформлять задачей его репозитория. Не менять `api/**`, миграции, Python-зависимости, CLI, его корневой `locales/**` и развёртывание. [Правила клиента](../../client/AGENTS.md).

Дерево исходных узлов нельзя восстановить из одного безопасного iframe: классы удалены, часть тегов заменена. Не ослаблять изоляцию и не загружать исходный сайт напрямую ради DOM. Новые данные передавать SYSTEM в API-004; рабочие селекторы по-прежнему проверяет API-002.

При передаче указать задачу, состояния, изменённый контракт, проверку и ограничения. Подробные критерии хранить в общем backlog, не создавать второй список задач в этом файле.


## Следующий участок после расписания

По поручению заказчика 23 ноября клиент SCALE-001 реализован отдельным экраном `/scout/storage`. Состояние и границы — IMPLEMENTATION_STATUS.md и FE-003/FE-004 общего backlog. Первоначальная CORS-блокировка обязательного `Idempotency-Key` локально снята отдельным исправлением SYSTEM: [PR ядра API](https://github.com/ergoms/ergo_ms_core_api/pull/8). Исправление вошло в ветку `dev` API-ядра. В живом браузере проверены закрепление и снятие защиты. Во FRONTEND CORS/ядро не менять и заголовок не убирать. 24 ноября на отдельной временной PostgreSQL через интерфейс проверены удаление HTML и одного старого комплекта результата с защитой двух последних. Затем проверено удаление связанных свежих JSON/CSV через локальный MediaClient с сохранением контрольных файлов. Автоматическая очистка проверена через UI-согласие и настоящий Beat на отдельном стенде: выключенная политика не удаляет, включённая создаёт одну операцию за дату UTC. Отдельно проверен RemoteMediaClient через HTTP настоящего media_api на временном хранилище: удаление старых JSON/CSV и сохранность контрольных файлов. Рабочие данные не затронуты; переход суток, внешний сервер/TLS и сетевые обрывы этим проходом не проверены. Для выбора из общего списка по-прежнему нужен API истории. Следующим отдельным этапом реализовано ручное сравнение по двум ссылкам сохранённых результатов; оно использует существующий GET compare без списка. Статус и границы живой проверки — IMPLEMENTATION_STATUS.md.
