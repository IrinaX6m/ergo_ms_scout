# FRONTEND — с чего начать

Ты отвечаешь за UX, дизайн и клиент Scout. Серверную часть ведёт команда SYSTEM. Сейчас задача — проектирование; первая работа — UX-002.

## Порядок изучения

1. [AGENTS.md](../../AGENTS.md) — общие правила и границы команды.
2. [DECISIONS.md](../DECISIONS.md) и [BEHAVIOR.md](../../BEHAVIOR.md) — что должен делать модуль.
3. [IMPLEMENTATION_STATUS.md](../IMPLEMENTATION_STATUS.md) и текущий `client/components/ScoutPage.vue` — что уже существует.
4. [UX.md](../UX.md), затем [DESIGN.md](../DESIGN.md) — сценарии, прототип и макеты.
5. [BACKLOG.md](../../BACKLOG.md) — задачи с ответственным FRONTEND; начать с UX-002.
6. [API_CONTRACT.md](../API_CONTRACT.md) — работающий API и недостающие расширения. Подробный протокол передачи — в [TEAM_WORKFLOW.md](../TEAM_WORKFLOW.md).

Исторические исследования и подробную серверную архитектуру изучать по необходимости, а не перед началом UX.

## Что сделать первым

Описать цели пользователя, входные данные, путь от источника к результату, ошибки и возвраты. Учесть все три способа настройки. Неподтверждённые предположения вынести в открытые вопросы; реальные интервью и проверки не придумывать.

Первый результат: сценарии и последовательность действий без детальной визуальной стилизации. SYSTEM параллельно уточняет данные и состояния в SPEC-001 и SPEC-002.

Далее: схемы экранов DES-001–DES-004 → проверка прототипа UX-003 → визуальные макеты DES-005 → выбранные задачи реализации клиента FE-001–FE-004 и UX-001. Полные условия завершения находятся только в backlog.

## Область работы

Код: `client/**`, включая строки интерфейса в `client/js/locales.js`. Документы: UX.md, DESIGN.md и согласованные макеты. Использовать компоненты и тему ERGOMS; изменения общего ядра выделять в отдельную задачу его репозитория.

Не менять `api/**`, модели, миграции, Python-зависимости, CLI и развёртывание. Корневой `locales/**` содержит справку CLI и относится к SYSTEM. Дополнительные правила для кода — в [client/AGENTS.md](../../client/AGENTS.md).

## Работа с SYSTEM

Если интерфейсу нужны новые данные или операция, описать потребность и связать задачу с API-001–API-003, SPEC-004 либо AI-001. Не придумывать несуществующий рабочий API. Для макетов и клиентской разработки допустимы явно обозначенные тестовые ответы по согласованному контракту.

При передаче указать задачу, сценарии и состояния, затронутый контракт, проверку и ограничения. Права, состояние запуска и подписи ссылок определяет сервер; клиентская проверка их не заменяет.
