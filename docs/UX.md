# SCOUT — разработка UX

Ответственная команда — FRONTEND. SYSTEM участвует как владелец данных, правил и состояний API. После обсуждения кликабельных эскизов 5 ноября 2026 года пользователь поручил реализовать пошаговый клиент. По сообщению заказчика проверка удобства ручного сценария прошла без замечаний. [UX-003](../BACKLOG.md#ux-003--проверка-прототипа-взаимодействия).

## Принятая последовательность

«Способ работы → Источник и правила → Предпросмотр → Подтверждение → Выполнение → Результат». Раздел «Настройки системы» открывает панель ядра и сохраняет текущую форму. Селекторы, цель и лимиты относятся к заданию. Решения — D-010 и D-011 в [DECISIONS.md](DECISIONS.md).

Ручной сценарий: пользователь задаёт URL и правила, получает примеры, проверяет значения и происхождение, переходит к подтверждению и только затем запускает сбор. Ошибка ввода привязана к полю. Пустой предпросмотр возвращает к правилам; ошибка отмены не сбрасывает текущий запуск. При потере связи сохраняется последнее состояние и продолжаются попытки обновления, а управляющие действия блокируются до получения достоверного состояния.

Визуальный и текстовый способы пока показывают доступность серверной функции, сохраняют адрес/черновик и предлагают ручной переход. Полный сценарий выбора элементов и обработки предложения модели остаётся зависимым от API-002 и AI-001. Отдельная загрузка страницы без правил также требует серверного контракта; текущий ручной API получает снимок в ходе предпросмотра.

Задачи ведутся в общем [BACKLOG.md](../BACKLOG.md): UX-002 — сценарии и структура взаимодействия, UX-003 — проверка прототипа. Существующая UX-001 относится к реализации выбора полей и не заменяет эту работу.

## Что нужно выяснить сначала

- Кто будет работать со Scout и насколько знаком с полями, селекторами и обходом сайтов.
- С чего человек начинает: адрес, список полей, пример страницы или описание цели.
- Как понимает, что получил нужный результат и может доверять найденным значениям.
- Когда нужно объяснение, исправление настроек или участие человека при ошибке.

Не придумывать выполненные интервью и подтверждённые типы пользователей. Реальных примеров сайтов пока нет; для обсуждения допустим явно обозначенный условный пример. Открытый вопрос о пользователях — Q-009 в [OPEN_QUESTIONS.md](OPEN_QUESTIONS.md).

## Первый результат: сценарии взаимодействия

Для каждого сценария описать цель, исходные данные, шаги, решение пользователя, ответ системы, ожидаемый итог и путь восстановления при ошибке. Включить:

1. Первый ручной сбор по адресу: поля, проверка примеров, подтверждение и результат.
2. Выбор полей на сохранённой странице: карточка, совпадения, пропуски и исправление предложения.
3. Настройка по описанию: предложение модели, ручная правка и подтверждение общего плана.
4. Изменение настроек после неудачного предпросмотра и создание нового задания без потери выбранного контекста.
5. Пауза, продолжение, отмена, потеря связи и возвращение к существующему запуску.
6. Понимание частичного результата, проверка происхождения и скачивание данных.

Отдельно разобрать переключение трёх способов настройки: какие данные сохраняются, что требует повторной проверки и как не запутать пользователя. Не переносить внутренние понятия worker'а и брокера в обязательные шаги человека.

Подтверждённые ограничения из [BEHAVIOR.md](../BEHAVIOR.md) сохраняются: один сбор, подтверждение плана, раздельные счётчики загрузки и извлечения, отсутствие вызовов LLM для основного извлечения.

## Параллельная работа SYSTEM

Пока FRONTEND описывает сценарии, SYSTEM выполняет проектирование SPEC-001 и SPEC-002: какие данные нужны и какие состояния возможны. Совместно сверить, что пользовательское действие имеет определённый серверный результат, отказ и способ восстановления.

Это не означает, что весь сервер нужно реализовать до начала UX. Существующий API и предлагаемые расширения отдельно описаны в [API_CONTRACT.md](API_CONTRACT.md). Новое желаемое поведение остаётся предложением, пока оно не согласовано.

## Дальнейший порядок

1. UX-002: сценарии и понятная последовательность действий.
2. DES-001–DES-004: схемы экранов и прототип переходов на основе сценариев, без обязательной детальной стилизации.
3. UX-003 — пройти прототип с заказчиком или будущим пользователем и зафиксировать замечания. Для ручного сценария проверка пройдена.
4. DES-005: визуальные макеты, компоненты и доступность с учётом исправленного взаимодействия.
5. Реализация выбранного участка: FRONTEND пишет клиент, SYSTEM — необходимую серверную часть. Интеграция опирается на согласованный контракт.

Уточнять модель и контракт можно на всех этапах. Полная визуальная отрисовка не должна предшествовать пониманию сценария, а проектирование UX не должно ждать завершения всех серверных функций.

## Что передать после проверки

Сценарии, прототип, перечень состояний и действий, замечания проверки, внесённые исправления и нерешённые вопросы. Для каждого вывода указать основание: подтверждённое требование, наблюдение проверки либо пока только предположение.

Для начала реализации конкретного участка должны быть понятны его шаги, ошибки и возвраты, необходимые данные API и визуальная основа. Непроверенный макет не считать доказательством удобства, а наличие маршрута в Vue — завершённым UX.
