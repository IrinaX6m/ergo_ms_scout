# SCOUT — граница FRONTEND и SYSTEM

Статус: начальное описание текущего кода для задачи API-001, 2 ноября 2026 года. Целевые расширения требуют согласования; этот файл не означает, что отсутствующие операции уже реализованы.

SYSTEM отвечает за соответствие описания серверу, FRONTEND — за проверку достаточности данных для интерфейса. Порядок изменений — в [TEAM_WORKFLOW.md](TEAM_WORKFLOW.md).

## Источник текущего поведения

- [urls.py](../api/urls.py) — пути операций внутри префикса `/api/scout/`.
- [views.py](../api/views.py) — методы, тела запросов и ответы.
- [present.py](../api/present.py) — поля ответов.
- [constants.py](../api/services/constants.py) — состояния и текущие ограничения.
- [integrations.py](../api/integrations.py) и [permissions.py](../api/permissions.py) — ошибки и права.
- [endpoints.js](../client/js/endpoints.js) — относительные адреса клиента; префикс и авторизацию добавляет общий `apiClient`.

Внешние идентификаторы — UUID в `public_id`. Числовые ключи БД в клиентский контракт не входят. Операции требуют аутентификации и соответствующих прав; доступ ограничен владельцем согласно текущему серверному коду.

## Работающие операции

Все пути ниже относительны к `/api/scout/`:

- `GET health/` — состояние модуля; это не публичная анонимная проверка.
- `GET jobs/` — объект с массивом `jobs`, сейчас не более 100 заданий.
- `POST jobs/` — создание задания; поля запроса: `title`, `seed_urls`, `fields`, `record`, `crawl`; ответ задания, HTTP 201.
- `GET jobs/{public_id}/` — задание и последняя версия плана.
- `PATCH jobs/{public_id}/` — новая версия настроек. Текущий обработчик ожидает адреса и поля плана; частичное изменение только заголовка не считать гарантированным сценарием.
- `POST jobs/{public_id}/explore/` — предварительная загрузка; ответ запуска, HTTP 202.
- `GET runs/{public_id}/` — состояние запуска. Перед подтверждением полный ответ может содержать предпросмотр. Для опроса прогресса есть `?summary=1`.
- `POST runs/{public_id}/approve/` — подтверждение версии плана.
- `POST runs/{public_id}/start/` — начало основного сбора; HTTP 202.
- `POST runs/{public_id}/pause/` — запрос паузы; ответ запуска.
- `POST runs/{public_id}/resume/` — продолжение; HTTP 202.
- `POST runs/{public_id}/cancel/` — запрос отмены; ответ запуска.
- `GET runs/{public_id}/records/` — объект с массивом `records`. Параметры `limit` и `cursor` включают постраничную выдачу.
- `POST runs/{public_id}/export/` с `kind: json` или `csv` — `download_url`, `filename`, `kind`. Подписанную ссылку формирует сервер; клиент её не вычисляет.

HTTP 202 означает принятие операции, а не завершение сбора. Для результата действия клиент читает состояние запуска. Подтверждение и старт — разные серверные операции, даже когда интерфейс объединяет их в одно действие.

## Основные ответы

Задание: `public_id`, `title`, `revision`. Версия может быть `null`; иначе содержит `public_id`, `revision_number`, `seed_urls`, `record`, `fields`, `limits`, `crawl`, `plan_hash`, `approved`. `record` может быть `null`. Поля версии определяются сервером, а не отдельным форматом для каждого способа настройки.

Запуск: `public_id`, `status`, `error_summary`, `job_public_id`, `plan_hash`, `crawl`, `approved`, `snapshot_count`, `record_count`, `stop_reason`, `frontier`, `journal`, `events`, `tasks`.

`frontier` содержит счётчики `queued`, `active`, `done`, `skipped`, `failed`. Каждая запись `tasks` содержит `public_id`, `kind`, `status`, `error_code`, `error_message`. Это состояния серверных задач; загрузку кнопки или несохранённую форму клиент ведёт отдельно.

`preview` присутствует не во всех ответах. В ожидании подтверждения он может содержать массив примеров с `source_url`, `values`, `evidence`; при ошибке предпросмотра — объект `error` с ошибкой Scout. Отсутствие поля, пустой массив и ошибка имеют разный смысл.

Запись результата: `public_id`, `values`, `evidence`. Текущее значение поля имеет `raw` и `normalized`; расширенные типы и вложенность предстоит согласовать в SPEC-001 и DATA-001. Evidence содержит `field_path`, `source_url`, `locator`, `raw_value`, `normalized_value`, `extractor_id`, `extractor_version`.

## Порции результата и опрос прогресса

- Первый запрос страницы выглядит как `GET runs/{public_id}/records/?limit=50`. Сервер возвращает `records` и `next_cursor`. Передайте полученный курсор в следующем запросе вместе с `limit`. `next_cursor: null` означает конец списка на момент запроса.
- `limit` принимает целое число от 1 до 200. Запрос с одним `cursor` использует 50 строк. Курсор — `public_id` последней показанной записи этого запуска. Неверный `limit` или `cursor` даёт HTTP 400 с кодом `invalid_limit` или `invalid_cursor`.
- Строки идут по времени создания со стабильным порядком при одинаковом времени. `Evidence` входит в каждую строку. Запрос без `limit` и `cursor` возвращает весь массив в прежнем формате. Для завершённого результата все порции образуют тот же набор записей, что и полная выдача.
- `GET runs/{public_id}/?summary=1` возвращает идентификаторы, состояние, подтверждение плана, причину остановки и счётчики `snapshot_count`, `record_count` и `frontier`. Для задач, журнала и предпросмотра запрашивайте полный ответ.
- Экспорт доступен после завершения сбора, включая завершение с ошибками. JSON содержит записи и Evidence, CSV — идентификаторы и нормализованные значения. Сервер формирует файл порциями и передаёт его в Media API, затем возвращает подписанную ссылку.

## Состояния и ошибки

Состояния запуска: `exploring`, `awaiting_confirmation`, `running`, `pausing`, `paused`, `cancelling`, `cancelled`, `completed`, `completed_with_errors`, `failed`.

UI не подменяет ответ сервера оптимистическим завершением паузы, отмены или всего сбора. При смене задания запоздалый ответ прежнего запроса не должен заменять текущие данные. Точный набор доступных действий и причин частичного результата уточняется совместно с макетами.

Ошибки Scout возвращаются как `code` и `detail`. `approval_required`, `slot_busy`, `plan_changed`, `invalid_state` дают HTTP 409; ошибка `media` — 503; остальные ошибки Scout — 400. Аутентификация, права и отсутствие объекта могут давать стандартные ответы DRF с `detail`, без `code`; клиент должен их различать.

## Сетевая политика загрузки HTML

Предпросмотр, сбор и визуальные снимки загружают публичные HTTP(S)-адреса через стандартные порты без учётных данных и прокси. На каждом редиректе Scout повторяет проверку назначения и соединяется с проверенным IP. В режиме обхода дополнительно проверяются разрешённые домены, а при основном сборе действуют фильтры переходов. Администратор может добавить точные пары IP и порта через `SCOUT_TRUSTED_FETCH_ENDPOINTS`, например `127.0.0.1:8765` или `[::1]:8765`. Исключение действует только для URL с указанным IP и портом.

Предел ответа по умолчанию — 1 000 000 байт до и после распаковки. Таймаут сетевой операции по умолчанию — 20 секунд, число редиректов ограничено пятью. У задач предпросмотра и сбора до трёх попыток при сетевой ошибке или HTTP 429, 500, 502, 503, 504. Запрещённое назначение (`url_blocked`), выход редиректа за границы плана (`redirect_scope`) и превышение размера (`too_large`) считаются окончательными ошибками загрузки.

## API-002 — серверный черновик для UX-001

Сервер поддерживает перечисленные операции. Формат и сценарий работы редактора предстоит согласовать с FRONTEND перед интеграцией.

- `POST visual-snapshots/` с `{"url":"https://example.com/catalog"}` — HTTP 202, `public_id` и `status: "loading"`. Снимок можно запросить до создания задания. Сервер загружает одну открытую HTML-страницу через очередь Scout. У загрузки предел 1 МБ и 30 запросов на пользователя в час (HTTP 429 при превышении).
- `GET visual-snapshots/{public_id}/` — HTTP 200, `public_id` и `status`. Пока снимок `loading`, клиент периодически запрашивает его состояние. Для `ready` сервер добавляет `final_url` и `html`. Для `failed` сервер добавляет `error: {"code":"not_html","detail":"Ответ не является HTML"}`. Если подготовка не закончилась за две минуты, возвращается `load_timeout`.
- `POST visual-snapshots/{public_id}/check/` — HTTP 200 с проверкой CSS на этой версии снимка. Готовый селектор передаётся как `kind: "css"` и `selector`. Чтобы получить предложение по клику, вместо этих полей передаётся `node_id`. Для снимка, который ещё загружается или завершился ошибкой, сервер возвращает HTTP 409 с `code: "snapshot_not_ready"`.

Для чтения и проверки требуются аутентификация и `scout_configure`, для загрузки дополнительно требуется `scout_run`. UUID закреплён за одной загрузкой. Просроченный через час или чужой снимок даёт HTTP 404. Для снимка действует общая сетевая политика загрузки HTML. Пользователь может повторить загрузку новым запросом.

`html` — структурное представление без сторонних стилей, скриптов, активных ссылок и загрузки ресурсов. Клиент должен отображать его в изолированном `iframe` с отключёнными скриптами. Атрибут `data-scout-node` связывает отображённые элементы с исходным снимком и используется только в его пределах.

Пример проверки поля после клика:

```json
{
  "record": {"kind": "css", "selector": "article.product"},
  "field": {"name": "price", "scope": "record", "many": false, "node_id": "n24"}
}
```

Чтобы предложить правило карточки отдельно, передайте `{"record":{"node_id":"n12"},"field":null}`. Для поля на всю страницу передайте `record: null` и `scope: "page"`. Если предлагаемый селектор не найден, сервер возвращает HTTP 400 с `selector_not_suggested`. Некорректные селекторы, неизвестный элемент или выбор за пределами карточки также дают HTTP 400 с `code` и `detail`.

Ответ содержит `record` и `field` в формате обычного плана либо `null`, `row_count` с общим числом строк и `rows` с примерами (до 20). Строка карточки содержит `node_id` для подсветки либо `null`, когда видимого элемента нет. При проверке поля в строку добавляются `match_count`, `match_node_ids` (до 20 видимых элементов) и `value` с `raw` и `normalized`. Ноль совпадений даёт `value: null`. При `many: false` возвращается первое значение, при `many: true` применяется формат нескольких значений существующего извлекателя. Проверка на снимке предшествует сохранению плана и обычному предпросмотру.

## Пока не реализовано

Клиент от 5 ноября 2026 года использует операции из раздела «Работающие операции». Экран подтверждения сам по себе не отправляет approve/start; они вызываются последовательно по явному действию пользователя. До старта проверяется совпадение `job_public_id`, `plan_hash` и сохранённой формы. Текущая таблица получает полный массив `records` и делит его на страницы на клиенте. Ключи `job`/`run` сохраняются в URL при переходе между порциями таблицы.

- Подключение визуального редактора к API-002 — UX-001.
- Предложение плана по описанию с LLM — AI-001.
- Управление профилями прокси — SPEC-004.
- Подключение серверной пагинации и компактного опроса прогресса в клиенте.
- Регистрация дополнительных исполнителей — отложенная DIST-001.

Пути и поля этих операций пока не закреплены. FRONTEND не придумывает их как рабочий API, SYSTEM не требует строить интерфейс на неописанных ответах. В API-001 добавить согласованные примеры для нужных экранов и явно помеченные изменения текущего формата.
