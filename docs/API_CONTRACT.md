# SCOUT — граница FRONTEND и SYSTEM

Статус: начальное описание текущего кода для задачи API-001, 2 ноября 2026 года. Целевые расширения требуют согласования; этот файл не означает, что отсутствующие операции уже реализованы.

SYSTEM отвечает за соответствие описания серверу, FRONTEND — за проверку достаточности данных для интерфейса. Порядок изменений — в [TEAM_WORKFLOW.md](TEAM_WORKFLOW.md).

## Источник текущего поведения

- [urls.py](../api/urls.py) — пути операций внутри префикса `/api/scout/`.
- [views.py](../api/views.py) — методы, тела запросов и ответы.
- [present.py](../api/present.py) — поля ответов.
- [constants.py](../api/services/constants.py) — состояния и текущие ограничения.
- [integrations.py](../api/integrations.py) и [permissions.py](../api/permissions.py) — ошибки и права.
- [endpoints.js](../client/js/endpoints.js) — относительные адреса клиента; префикс и авторизацию добавляет общий `apiClient`.

Внешние идентификаторы — UUID в `public_id`. Числовые ключи БД в клиентский контракт не входят. Операции требуют аутентификации и соответствующих прав; доступ ограничен владельцем согласно текущему серверному коду.

## Работающие операции

Все пути ниже относительны к `/api/scout/`:

- `GET health/` — состояние модуля; это не публичная анонимная проверка.
- `GET jobs/` — объект с массивом `jobs`, сейчас не более 100 заданий.
- `POST jobs/` — создание задания; поля запроса: `title`, `seed_urls`, `fields`, `record`, `crawl`; ответ задания, HTTP 201.
- `GET jobs/{public_id}/` — задание и последняя версия плана.
- `PATCH jobs/{public_id}/` — новая версия настроек. Текущий обработчик ожидает адреса и поля плана; частичное изменение только заголовка не считать гарантированным сценарием.
- `POST jobs/{public_id}/explore/` — предварительная загрузка; ответ запуска, HTTP 202.
- `GET runs/{public_id}/` — состояние запуска; перед подтверждением может содержать предпросмотр.
- `POST runs/{public_id}/approve/` — подтверждение версии плана.
- `POST runs/{public_id}/start/` — начало основного сбора; HTTP 202.
- `POST runs/{public_id}/pause/` — запрос паузы; ответ запуска.
- `POST runs/{public_id}/resume/` — продолжение; HTTP 202.
- `POST runs/{public_id}/cancel/` — запрос отмены; ответ запуска.
- `GET runs/{public_id}/records/` — объект с массивом `records`. Порции строк и курсор сейчас не реализованы.
- `POST runs/{public_id}/export/` с `kind: json` или `csv` — `download_url`, `filename`, `kind`. Подписанную ссылку формирует сервер; клиент её не вычисляет.

HTTP 202 означает принятие операции, а не завершение сбора. Для результата действия клиент читает состояние запуска. Подтверждение и старт — разные серверные операции, даже когда интерфейс объединяет их в одно действие.

## Основные ответы

Задание: `public_id`, `title`, `revision`. Версия может быть `null`; иначе содержит `public_id`, `revision_number`, `seed_urls`, `record`, `fields`, `limits`, `crawl`, `plan_hash`, `approved`. `record` может быть `null`. Поля версии определяются сервером, а не отдельным форматом для каждого способа настройки.

Запуск: `public_id`, `status`, `error_summary`, `job_public_id`, `plan_hash`, `crawl`, `approved`, `snapshot_count`, `record_count`, `stop_reason`, `frontier`, `journal`, `events`, `tasks`.

`frontier` содержит счётчики `queued`, `active`, `done`, `skipped`, `failed`. Каждая запись `tasks` содержит `public_id`, `kind`, `status`, `error_code`, `error_message`. Это состояния серверных задач; загрузку кнопки или несохранённую форму клиент ведёт отдельно.

`preview` присутствует не во всех ответах. В ожидании подтверждения он может содержать массив примеров с `source_url`, `values`, `evidence`; при ошибке предпросмотра — объект `error` с ошибкой Scout. Отсутствие поля, пустой массив и ошибка имеют разный смысл.

Запись результата: `public_id`, `values`, `evidence`. Текущее значение поля имеет `raw` и `normalized`; расширенные типы и вложенность предстоит согласовать в SPEC-001 и DATA-001. Evidence содержит `field_path`, `source_url`, `locator`, `raw_value`, `normalized_value`, `extractor_id`, `extractor_version`.

## Состояния и ошибки

Состояния запуска: `exploring`, `awaiting_confirmation`, `running`, `pausing`, `paused`, `cancelling`, `cancelled`, `completed`, `completed_with_errors`, `failed`.

UI не подменяет ответ сервера оптимистическим завершением паузы, отмены или всего сбора. При смене задания запоздалый ответ прежнего запроса не должен заменять текущие данные. Точный набор доступных действий и причин частичного результата уточняется совместно с макетами.

Ошибки Scout возвращаются как `code` и `detail`. `approval_required`, `slot_busy`, `plan_changed`, `invalid_state` дают HTTP 409; ошибка `media` — 503; остальные ошибки Scout — 400. Аутентификация, права и отсутствие объекта могут давать стандартные ответы DRF с `detail`, без `code`; клиент должен их различать.

## Пока не реализовано

Клиент от 5 ноября 2026 года использует только перечисленные выше операции. Экран подтверждения сам по себе не отправляет approve/start; они вызываются последовательно по явному действию пользователя. До старта проверяется совпадение `job_public_id`, `plan_hash` и сохранённой формы. Пагинация результата выполняется над всем массивом `records` на клиенте и не означает готовность серверной API-003. Ключи `job`/`run` сохраняются в URL при переходе между порциями таблицы.

- API выдачи снимка для интерактивного выбора DOM-элементов и проверки предложенных правил — API-002.
- Предложение плана по описанию с LLM — AI-001.
- Управление профилями прокси — SPEC-004.
- Порции результатов и согласованный контракт большого экспорта — API-003.
- Регистрация дополнительных исполнителей — отложенная DIST-001.

Пути и поля этих операций пока не закреплены. FRONTEND не придумывает их как рабочий API, SYSTEM не требует строить интерфейс на неописанных ответах. В API-001 добавить согласованные примеры для нужных экранов и явно помеченные изменения текущего формата.
