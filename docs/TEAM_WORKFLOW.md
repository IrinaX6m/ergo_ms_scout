# SCOUT — взаимодействие команд

Задачи и состояния ведутся только в [BACKLOG.md](../BACKLOG.md). У каждой задачи один ответственный. Базовый клиент и сервер уже работают; новые участки проходят проектирование и интеграцию без повторного старта всего проекта. Текущее поручение касается задач и документации, запуск служб не требуется.

## Границы

- [FRONTEND](teams/FRONTEND.md): UX, дизайн и `client/**`. Инструкции для кода — [client/AGENTS.md](../client/AGENTS.md).
- [SYSTEM](teams/SYSTEM.md): API и остальная система, включая зависимости, CLI и его корневой `locales/**`. Инструкции — [api/AGENTS.md](../api/AGENTS.md).
- Общие требования, решения и backlog изменяются согласованно. Чтение чужого кода допустимо; необходимость правки чужой области оформляется связанной задачей, а не скрытой частью своей.
- Изменение общего ядра ERGOMS выделяется в отдельную задачу соответствующего репозитория.

## Текущий порядок: инспектор блоков

1. FRONTEND — UX-004 на работающем UX-001: связанный выбор блоков и DOM, состояния, проверка прототипа.
2. SYSTEM предоставляет реализованный и проверенный API-004: метаданные исходных узлов, лимиты и совместимость с API-002. Уточнения потребителя обсуждаются во время UX, а не после финальных цветов; сервер дерева не создаётся повторно.
3. FRONTEND — DES-006 на основе существующей темы/компонентов; затем FE-005 после согласования взаимодействия и данных.
4. FE-004 и совместная приёмка нового участка. Тестовые ответы не заменяют API и проверку прав.

UX-002/DES-001–DES-005 остаются основой и уточняются точечно. Ручной UX-003 принят, базовый UX-001 реализован. Клиент ИИ/прокси и больших результатов остаётся FE-001–FE-003: эти участки не нужно ожидать как отсутствующий сервер. Дальнейшее изменение приоритета фиксируется в backlog.

## Контракт и зависимости

[API_CONTRACT.md](API_CONTRACT.md) описывает текущую границу и отсутствующие расширения. SYSTEM отвечает за соответствие серверу, FRONTEND — за достаточность данных для интерфейса. До интеграции согласовать метод, путь, запрос и ответ, типы и пустые значения, состояния, ошибки, права и совместимость.

- API-002 обеспечивает снимки и проверку правил для работающего UX-001. API-004 реализован для исходных меток DOM и FE-005; не ослабляет изоляцию снимка.
- AI-001 формирует предложение модели; FE-001 отвечает за клиентское описание цели и отображение предложения.
- SPEC-004 определяет профиль прокси и его API; FRONTEND делает форму по этому решению.
- API-003 обеспечивает выдачу большого результата для FE-003.

Для параллельной клиентской разработки допустимы явно обозначенные тестовые ответы. Они не подтверждают готовность сервера. Если контракт меняется, указать затронутые сценарии и способ перехода со старого формата.

## Передача результата

Указать идентификатор задачи, что готово, изменение контракта, примеры, результат проверки и ограничения. Требования обновлять в BEHAVIOR.md и DECISIONS.md, UX и макеты — в профильных документах, факт реализации — в IMPLEMENTATION_STATUS.md.

Отдельная клиентская или серверная проверка закрывает задачу этой команды. Полный сценарий готов после совместимой работы обеих частей на согласованных данных.
